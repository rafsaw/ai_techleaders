# D18 — Text-session experience and delivery

- Date, owner: 2026-11-05, product owner.
- Origin: PO-approved E05 gate decisions and independent review B1/S1–S10. These are product and design choices for a course project, not new evidence of demand.
- Decision: One E05 specification covers stories #44 and #45 in two implementation phases. The confirmed E04 booking is the session identity; its participant-only `/bookings/[id]` page becomes the single booking/session screen. Participants can read retained past messages; the retention/deletion policy is deferred, with no automatic deletion and no promise of permanent storage. E05 has no edit, unsend or delete action; a participant can send a follow-up correction only while the booked window is open. A message has at most 4,000 Unicode code points. History is shown 100 messages at a time with Earlier messages navigation to all retained messages.
- Delivery: During an open booked window, the newest message view polls through the existing authenticated API every five seconds only while the tab is visible. Polling pauses for a hidden tab or an older-history page. Returning to a visible newest page refreshes immediately; at the exact booked end, a visible newest page stops sending and recurring polling and performs one final message read. A hidden or older page makes no background request at end; opening Latest messages or returning to the tab reads the retained history. Past sessions do not poll. No WebSocket, external chat service, scheduler or shared polling infrastructure.
- Relationship to earlier decisions: D10's server-enforced 25/50-minute window, participant-only access and sufficiency of refresh remain active; D18 specifies the refresh cadence and UI. D15's private list remains. D12's cancellation, no-show, refund and dispute processes remain outside E05. D17's payment-confirmation contract remains. E04 must prevent self-booking before creating a Booking; E05 reuses E04's single detail route.
- Consequences: Each visible active tab creates ordinary authenticated reads and therefore E01 request-based session activity. Use the existing per-user PostgreSQL rate limiter with headroom over the polling cadence. The client may lag by five seconds plus request latency. Message sends remain repeat-safe through `clientMessageId`; server time, not browser timers, decides whether sending is allowed. Do not enable real-user Checkout until E05's exchange works and E04's release conditions pass.
- Status: active. Supersedes: no prior brief decision; refines D10 and D15. Review by: E05 implementation review. Required path to change: a superseding decision approved by the product owner.
