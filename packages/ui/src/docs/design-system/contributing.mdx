# Contributing

Start with the specified user task and an existing pattern. The package is a documented
system for building screens; a missing need goes to What is missing before it becomes a
new dependency, component or variant (prompt rules 1, 6 and 12; stage 4 Contributing).

Sources are `lekcja-06/prompt-storybook.md`, `lekcja-06/tokeny.md`,
`packages/ui/POSTEP.md`, root `AGENTS.md` and the product brief/specifications in `.ai/specs/`.
PO below means Rafał, the recorded product owner; product decisions require his approval
(brief: decider for scope; POSTEP approved decisions).

## New-component documentation contract

Every primitive/product component page includes all thirteen sections; if one does not
apply, explain why (prompt stage 2):

1. The user problem in one sentence.
2. Concrete DevMentor situations to use it.
3. When not to use it and the alternative.
4. Anatomy, including optional parts.
5. Every variant and its selection rule.
6. Default, hover, focus, pressed, disabled, pending, selected and error states where applicable; explain unavailable actions.
7. Keyboard, focus, semantics, announcements and minimum target size.
8. Labels, length, long text, numbers and longer translations.
9. Behaviour at 320, 768 and 1440 px.
10. Typed API, defaults and prop descriptions.
11. Minimal code and a realistic product example.
12. Good/bad pairs with a reason for each.
13. Related components and patterns.

Rules carry a reference/anti-reference, brief/spec decision, WCAG or WAI-ARIA source.
Unsourced choices are explicitly labelled proposals and reported to the PO (prompt rule 4).
Pattern pages use their separately approved nine-section contract rather than pretending
to be primitives (P-PT1: proposal approved by Rafał).

## Approval and review

The PO approves product/style choices, new scope and changes to existing system assets;
record approval and unresolved questions in POSTEP. A contributor may investigate, write
an explicit proposal and prepare its reviewable evidence; an unapproved proposal is not a
new system rule (brief scope decider; prompt rules 1, 4, 6, 12).

Use source/spec review, validation and rendered-browser evidence for technical review.
The materials do not name another standing design-system maintainer; do not invent a
second approver. Stage work stops for the PO's “dalej” before the next stage. Do not push
or publish during this exercise (prompt workflow and rule 11).

## Commands and completion evidence

Run from the repository root (AGENTS commands; POSTEP technical plan):

```sh
npm run storybook
npm run build-storybook
npm run check:tokens
npm run test:storybook
npm run test:storybook:themes -w @devmentor/ui
npm run lint
npm run typecheck
npm run build
npm run test:coverage
npm run test:integration:install
npm run test:integration
```

`storybook` opens the local documentation server; `build-storybook` produces the static
site; `check:tokens` rejects raw colours, palette classes and arbitrary Tailwind values.
`test:storybook:themes` runs story interactions/a11y in both themes (POSTEP technical plan).
Integration tests require Docker and the production build and must not silently skip
(AGENTS testing rules).

All configured gates must pass before calling a change complete. Changed runtime files
require 100% per-file unit coverage; stories have their own interaction/a11y runner.
Browser review covers widths 320/768/1440, both themes, keyboard and overlays. Record
what was actually checked, unresolved gaps and proposals, rather than equating a build
with a visual or accessibility pass (AGENTS testing; prompt stage 5).

Keep the run log in `.ai/runs/`, update the relevant spec and POSTEP, and update the
agent guide/component catalogue when the system contract changes. For this exercise,
changes outside the design-system directory are limited to the explicitly authorized
wiring and agent-guide work; pending application/spec corrections stay listed in POSTEP
until their separate implementation task (AGENTS SDD; prompt rule 11; POSTEP outside-system list).
